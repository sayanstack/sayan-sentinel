# Target Authorization

Target Authorization is what turns "a URL" into something Sentinel is
allowed to reach at all. A URL appearing anywhere in source, a README, an
environment variable, an issue, a PR, scanner output, or AI output never
constitutes authorization to scan it — only an explicit, persisted,
verified `TargetAuthorization` record does, and Scope Guard is the only
code path that consults it.

## What already existed vs. what this pass added

The Prisma model (`packages/database/prisma/schema.prisma`) and the
deterministic decision function (`evaluateScopeGuard`, see
[docs/scope-guard.md](scope-guard.md)) both predate this pass. What was
missing — and what this pass adds — is everything between them: an actual
API to create/verify/list/revoke a target, and the wiring that turns a
persisted DB row into the shape `evaluateScopeGuard` and `SafeHttpClient`
consume.

- Added `verificationChallenge` to the `TargetAuthorization` model — the
  random per-attempt token a domain owner publishes or serves was
  generated by `@sayan-sentinel/hexstrike-adapter`'s `target-verification`
  primitives (see [docs/scope-guard.md](scope-guard.md)) but had nowhere
  to persist between "create" and "verify." (No migration has been run
  against a live database in this environment — the schema change is
  real and the Prisma client regenerates from it, but there's no Postgres
  here to `prisma migrate dev` against; this is the same honesty note
  every other schema change in this project carries.)
- New `apps/api/src/targets/`: `TargetsController` + `TargetsService`
  implementing the full lifecycle.
- New `apps/api/src/audit/write-audit-event.ts`: the first code in this
  repository that actually writes to the `AuditEvent` table (it existed
  in the schema since an earlier phase but nothing used it). Never
  throws — an audit-write failure must not fail the operation it's
  recording.
- Activated NestJS's global `ValidationPipe` in `main.ts`. `class-
validator`/`class-transformer` were declared dependencies since the
  project's early scaffolding but never actually wired up — `CreateTargetDto`
  is the first DTO in this codebase whose `@IsIn`/`@IsInt`/etc decorators
  do anything, since nothing was enforcing them before.
- New `apps/api/src/targets/to-scope-guard-record.ts` — the actual
  unblocking piece: converts a persisted `TargetAuthorization` row into
  the `TargetAuthorizationRecord` shape `evaluateScopeGuard` expects.
  Tested by feeding the converted record into the _real_
  `evaluateScopeGuard` function (not a mock) and confirming it genuinely
  accepts a verified target and genuinely rejects a revoked one — proving
  the two previously-separate layers (persistence, Scope Guard) are
  actually compatible, not just structurally similar on paper.

## API

Auth is the same `x-demo-user-id`/`x-demo-organization-id` header stand-in
`RepositoriesController` uses — not a finished session layer, documented
identically.

- `POST /targets` — create. Body: `{ scheme, host, port, allowedPathPrefixes?, verificationMethod, expiresInDays?, maxTier?, repositoryId? }`. `verificationMethod` is restricted to `DNS_TXT`/`HTTP_WELL_KNOWN` — the schema's third value, `OWNERSHIP_CONFIRMATION`, has no verification primitive implemented yet, so the DTO doesn't accept it rather than accepting a request it can't honor. Generates the verification challenge server-side; a caller never supplies one.
- `GET /targets` — list, scoped to the caller's organizations.
- `GET /targets/:id` — single lookup; 404 (never 403) for a cross-tenant request, matching the platform-wide IDOR-safety convention.
- `POST /targets/:id/verify` — re-checks revoked/expired state _before_ attempting verification (a revoked or expired target is never re-verified even if its DNS/HTTP challenge would still technically resolve), then runs the real `dns_txt`/`http_well_known` primitive and sets `verifiedAt` only on success.
- `POST /targets/:id/revoke` — sets `revokedAt`; irreversible via this API (matching "immediate revocation" from the spec).

Every create/verify-attempt/verify-success/verify-failure/revoke writes an
`AuditEvent` row (`TARGET_CREATED`, `TARGET_VERIFICATION_STARTED`,
`TARGET_VERIFIED`, `TARGET_VERIFICATION_FAILED`, `TARGET_REVOKED`).

## What's still NOT here

- No re-verification-on-expiry scheduling (a background job that
  proactively re-checks targets approaching expiry) — verification is
  caller-triggered only.
- No UI — this is API-only.
- No wiring from a real scan job to look up a `TargetAuthorization` by ID
  and pass it through `toScopeGuardRecord` into `SafeHttpClient` or the
  HexStrike provider — that integration (a worker job type) doesn't exist
  yet.
- `OWNERSHIP_CONFIRMATION` remains an unimplemented verification method.
- No rate limiting on verification attempts (a caller could hammer
  `/verify` repeatedly) — acceptable for now since the underlying
  DNS/HTTP calls are themselves timeout-bounded and Scope-Guard-checked,
  but worth adding before any hosted deployment.

## Testing

13 new tests in `apps/api/src/targets/`: full CRUD + cross-tenant IDOR
regression coverage (mirroring `repositories.service.spec.ts`'s
established pattern) for `TargetsService`, plus a real (non-mocked)
integration test proving a converted DB record is genuinely accepted or
rejected by `evaluateScopeGuard`.
